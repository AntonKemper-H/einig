# C1 – Deployment on Render with hosted Postgres

Branch: `feature-c1-deployment`
Tests: `tests/test_deployment.py`

## Why
Render has a temporary disk, so a SQLite file there is deleted on every restart and all rooms would disappear mid-demo (`docs/decisions.md`, D4). The deployed app must therefore store its data in hosted Postgres (Neon or Supabase) via the secret `DATABASE_URL`, while local runs and all tests keep using a temporary SQLite file – and teammates keep writing ordinary SQL with `?` placeholders in `app/db.py`.

## What

### Choosing the database
- [ ] Real run (no test config): if the environment variable `DATABASE_URL` is set and not blank, `app.config["DATABASE_URL"]` holds it; otherwise the app uses the SQLite file `instance/einig.sqlite` as before and `DATABASE_URL` is not in the config.
- [ ] Edge case: a `DATABASE_URL` that contains only spaces counts as not set (SQLite is used).
- [ ] Rejected: a `DATABASE_URL` that does not start with `postgres://` or `postgresql://` stops the app with a `RuntimeError` that names `DATABASE_URL` but **never contains the value itself** (it holds the password).
- [ ] Creating the app does not open a database connection, so `GET /health` answers `ok` even when the database is unreachable.
- [ ] Tests always use a temporary SQLite file, even when `DATABASE_URL` is set in the environment (the test config ignores the environment).

### One interface for both databases (`app/db.py`)
- [ ] `get_db()` returns an object with `execute(sql, params)`, `commit()`, `rollback()` and `close()`. `execute` returns a cursor with `fetchone()` / `fetchall()`, and rows can be read by column name (`row["value"]`) on both databases.
- [ ] Code outside `db.py` writes SQL with `?` placeholders only. For Postgres, `db.to_postgres_sql(sql)` translates `?` to `%s`, leaves `?` inside quoted text alone, and doubles a literal `%` to `%%` (psycopg would otherwise read it as a placeholder).
- [ ] On Postgres, `get_db()` connects with `psycopg.connect(DATABASE_URL, row_factory=dict_row)` and sends no SQLite-only `PRAGMA`. The connection is closed at the end of the request.
- [ ] `init-db` on Postgres runs `schema.sql` translated by `db.schema_to_postgres(script)`: comments removed, `INTEGER PRIMARY KEY` becomes `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` (so ids count up by themselves), and `INSERT OR IGNORE INTO … ;` becomes `INSERT INTO … ON CONFLICT DO NOTHING;`. `schema.sql` stays the single source and is written in SQLite style.
- [ ] `reset-db` on Postgres finds the tables via `information_schema.tables` (schema `public`) and drops each with `DROP TABLE "<name>" CASCADE`; it never uses `sqlite_master` or `PRAGMA`.
- [ ] `db.INTEGRITY_ERRORS` is a tuple containing `sqlite3.IntegrityError` and `psycopg.IntegrityError`, so code can catch a broken UNIQUE rule (e.g. a second veto) the same way on both databases.
- [ ] Accepted: an `INSERT … RETURNING id` works through `get_db()` on SQLite (teammates use `RETURNING id` instead of SQLite's `lastrowid`, which Postgres does not have).
- [ ] Rejected: a duplicate key raises one of `db.INTEGRITY_ERRORS` and leaves the saved row unchanged.
- [ ] After a restart (a new app object on the same database), accepted rows are still there.

### Hosting config
- [ ] `render.yaml` describes one free Python web service: build with `uv sync --frozen --no-dev`, start with `init-db` (safe, never deletes) followed by `gunicorn` on `$PORT`, health check path `/health`.
- [ ] `render.yaml` lists `SECRET_KEY`, `DATABASE_URL`, `GOOGLE_MAPS_API_KEY` and `GOOGLE_MAPS_EMBED_KEY` without any value (`sync: false`, or `generateValue: true` for `SECRET_KEY`). No secret ever appears in the repository.
- [ ] New pinned dependency `psycopg[binary]==3.3.9`, added with `uv add` (approved by the Track C owner, 2026-11-13). Python has no built-in Postgres driver; `[binary]` ships the compiled C library, so Render needs no system packages.

## Out of scope
- No tables for rooms, participants, options, votes or vetoes; `schema.sql` belongs to Track A. C1 only makes sure the schema can run on Postgres.
- No SQLAlchemy or other ORM, no second schema file for Postgres.
- No tests that talk to a real Postgres server or to Render. A fake `psycopg.connect` is used instead; the real database is checked by hand after deploying.
- No Google Maps code, no `requests`, no PWA files (C2 and later).
- Do not create or edit `.env`, and never write a real `DATABASE_URL`, password or key anywhere in the repository.
- Creating the Render account and the Neon/Supabase database and entering the secrets in Render is done by a human, not by the agent.

## Done when
- All tests in `tests/test_deployment.py` and all earlier tests pass (`uv run pytest`), output pasted.
- The app runs at a public Render URL; `/health` answers `ok`.
- Accepted change survives a restart on Render: a row written on the deployed app is still there after "Manual Deploy → Restart service" (checked by hand, because there are no room features yet: via `init-db` output / the Neon SQL console).
- Rejected: starting with an invalid `DATABASE_URL` fails with a clear message that does not show the URL.
- `README.md` contains the deployed URL and the deployment steps.
